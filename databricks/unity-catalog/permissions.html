Unity Catalog permissions

Status: Last updated: 2026-11-11

Key concept and sub-topics

  • Three-level namespace. catalog.schema.table, all under one metastore per region.
  • Privileges inherit downward. A grant on a catalog applies to every schema and table inside it, including future ones.
  • Reading a table needs three grants: USE CATALOG on the catalog, USE SCHEMA on the schema, and SELECT on the table. Missing the first two is the most common "permission denied" surprise.
  • Grant to groups, not users. Manage membership in your identity provider and keep grants stable.
  • Ownership. The owner holds all privileges on an object and can grant them. Prefer a group as owner so access survives people leaving.
  • Fine-grained control. Row filters and column masks attach SQL functions to a table so different groups see different rows or masked values. Newer attribute-based access control builds on tags; check the current docs for availability before relying on it.
  • Securables beyond tables: views, volumes, functions, registered models, external locations and storage credentials.

Architecture: hierarchy and inheritance

Example

GRANT USE CATALOG ON CATALOG sales TO `analysts`;
GRANT USE SCHEMA  ON SCHEMA  sales.gold TO `analysts`;
GRANT SELECT      ON TABLE   sales.gold.orders TO `analysts`;

-- Column mask: only HR sees full SSN
CREATE FUNCTION sales.gold.mask_ssn(ssn STRING)
  RETURN CASE WHEN is_account_group_member('hr') THEN ssn ELSE '***-**-****' END;
ALTER TABLE sales.gold.customers ALTER COLUMN ssn SET MASK sales.gold.mask_ssn;
AI angle: the same grants govern registered models and functions that agents call as tools. An agent running as a service principal can then only reach data and tools that principal has been granted, which is the safest default for AI workloads.

Interview questions

A user has SELECT on a table but gets "permission denied". Why?Most likely they lack USE CATALOG or USE SCHEMA on the parents. SELECT alone is not enough.
Row filter vs dynamic view: when would you choose each?Row filters and column masks attach to the table itself, so the policy follows it everywhere. Dynamic views are an older pattern where the policy lives in a separate view that users must query instead.
How do you give a team read access to all current and future tables in a schema?Grant USE CATALOG on the catalog, USE SCHEMA on the schema and SELECT on the schema to a group. Privileges inherit downward, so new tables in that schema are covered automatically.
