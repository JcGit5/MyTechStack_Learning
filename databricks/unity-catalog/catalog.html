Catalog

Status: AI Last updated: 2026-11-11

Key concept and sub-topics

  • What it is. The top level of the three-level namespace catalog.schema.table. A catalog holds schemas, which hold tables, views, volumes, models and functions. It is registered in a metastore (one metastore per region in an account).
  • Purpose: a unit of isolation. Each catalog should stand for one boundary of data access. Common mappings are environment (dev, prod), team or business domain.
  • Catalog types. A standard catalog organizes your own data. A foreign catalog mirrors an external database for read-only queries (Lakehouse Federation). A shared catalog is created from a share another party provides (Delta Sharing, covered as its own topic later).
  • Catalogs you get automatically.
    • hive_metastore: objects from the legacy Hive metastore. Treat it as legacy; the docs mark the Hive metastore as deprecated.
    • Workspace catalog: created in new workspaces, usually named after the workspace. All users in that workspace can use it by default.
    • __databricks_internal: internal state for features such as pipelines and dashboards. Do not query, change or delete it.
    • Also commonly seen: system (system tables) and samples (sample data). These were not on the docs pages I read, so verify.
  • Default catalog. Used when a query leaves the catalog name out. For automatically enabled workspaces it is the workspace catalog, and a workspace admin can change it.
  • Managed storage. A catalog normally has its own managed storage location, where its managed tables and volumes are stored. Catalogs without one use the metastore-level location, and a schema can have its own location for finer isolation. The location must come from an external location. If the metastore has no storage location, you must give one when creating a catalog.
  • Workspace binding. Limits which workspaces can see a catalog, for example production data only in the production workspace. With no binding, every workspace attached to the metastore can access the catalog. Bound workspaces get Read & Write by default and can be set to Read Only.
  • What creation gives you. Every new catalog gets two schemas, default and information_schema. By default all account users get BROWSE, which lets them discover metadata without reading data.
  • Privileges to create. CREATE CATALOG on the metastore. Naming a managed location also needs CREATE MANAGED STORAGE on that external location. A foreign catalog needs CREATE FOREIGN CATALOG on the connection, or ownership of it. Compute needs a Unity Catalog-compliant access mode (SQL warehouses always qualify).
  • Access to anything inside. Needs USE CATALOG on the catalog, so a catalog is the first gate. Grants then inherit downward. See Permissions.
CREATE CATALOG IF NOT EXISTS prod
  MANAGED LOCATION 'abfss://uc@mystorage.dfs.core.windows.net/prod'  -- optional, path comes from an external location
  COMMENT 'Production data';

USE CATALOG prod;
SHOW SCHEMAS;   -- default, information_schema, plus yours
AI angle: registered models and functions that agents call live in schemas inside catalogs. Putting production AI assets in a catalog bound only to the production workspace is a simple way to keep experiments away from them.

Interview questions

What is a catalog in Unity Catalog and how do teams usually organize them?It is the top level of catalog.schema.table and a unit of data isolation. Teams usually split by environment (dev, prod), team or business domain, so that access and storage can be managed per boundary.
Standard vs foreign catalog?A standard catalog holds data managed in Unity Catalog. A foreign catalog is part of Lakehouse Federation: it mirrors an external database so you can query it read-only without copying the data.
Where is a catalog's managed data stored, and what if no location is set?In the catalog's managed storage location, which must come from an external location. If none is set it falls back to the metastore-level location, and if the metastore has none either, you must specify one when creating the catalog. A schema can override it for finer isolation.
How do you keep a production catalog out of a dev workspace?Bind the catalog to the production workspace only. Without a binding, every workspace attached to the metastore can access it.
A user cannot see anything in a catalog. What do you check?Whether they have USE CATALOG (and USE SCHEMA plus the object privilege below it), whether the catalog is bound to the workspace they are using, and whether they only have BROWSE, which shows metadata but not data.
Which privilege lets someone create a catalog?CREATE CATALOG on the metastore. Specifying a managed location additionally needs CREATE MANAGED STORAGE on the external location.
