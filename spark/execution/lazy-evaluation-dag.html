Lazy evaluation and the DAG

Status: Last updated: 2026-11-11

Key concept and sub-topics

  • Transformations are lazy. select, filter, join and groupBy only add to a plan. Nothing runs yet.
  • Actions trigger execution. count, collect, show and write make Spark plan and run a job.
  • Catalyst optimizes before running. Unresolved logical plan, then analyzed, then optimized logical plan (predicate pushdown, column pruning), then physical plan.
  • Narrow vs wide dependencies. Narrow ones (map, filter) stay inside a stage. Wide ones (groupBy, join) need a shuffle and start a new stage.
  • Job, stage, task. One action creates a job, shuffle boundaries split it into stages, and each stage runs one task per partition.
  • Recomputation. Each action replays the lineage from the source unless you cache() or persist() the result.

Architecture: from code to tasks

Example

df = spark.read.parquet("orders")          # lazy
big = df.filter("amount > 100")             # lazy, narrow
agg = big.groupBy("country").count()        # lazy, wide: shuffle here
agg.explain("formatted")                    # inspect the plan
agg.write.mode("overwrite").parquet("out")  # ACTION: job starts
AI angle: the plan is plain text, so you can paste explain("formatted") output into an LLM to get a first-pass tuning review. Verify any advice against the Spark UI before changing production jobs.

Interview questions

Why does a groupBy create a new stage?Rows with the same key must land on the same partition, so data is redistributed across the network (a shuffle). Spark cannot pipeline across that boundary.
If I call count() and then write() on the same DataFrame, how many times is the source read?Twice, unless it is cached. Each action replays the lineage.
What is the difference between a transformation and an action?Transformations (filter, select, groupBy) lazily extend the plan and return a new DataFrame. Actions (count, collect, write) trigger execution and return a result or write output.
